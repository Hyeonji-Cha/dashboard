Airflow와 Spark의 역할 차이

Airflow (누가, 언제, 어떤 작업을)

요청 JSON 검사 → 제출 Pod 생성 → Spark 종료 확인 → 공개 태스크 실행 → DAG 성공/실패 기록

Spark (실제 데이터 계산)

원천 파일 읽기 → 규칙 검사 → Silver 정제 → Gold A 집계 → S3 Parquet·manifest 쓰기

Silver: 오류 근거

dq_results / dq_order_results / quarantined_records / order_amount_checks

행 오류·활성 오류(active)·주문별 금액 MISMATCH를 분리해 저장. Bronze v2 결제 과거 오류는 active=false로 보존할 수 있어.

Gold A: 영향 범위

refresh_holds / held_scopes / previous_run_id

오염된 집계 범위를 보류하고 이전 정상 값이 있으면 표시해. 과거 정상 값이 없으면 0으로 채우지 않아.

R6·조사 에이전트: 재판정

silver_runs + order_amount_checks → R6 소비

완료된 검사를 순서대로 읽고, 후속 PASS를 바탕으로 해소 여부를 재판정해야 해. R6 순차 소비·VERIFIED까지는 다른 담당의 운영 연결이 남아 있어.

파일·manifest는 정확히 어디에 존재할까?

데이터 파일과 작업 지시서와 실행 증거는 달라. 현재 코드를 기준으로 실제로 읽는 것과 참고자료인 것을 구분했어.

같은 run_id 안에서 데이터가 어떻게 연결될까?

입력 확인

출력 증명

Silver/manifest.json
어느 원본을 읽었고 몇 건·무슨 스키마를 생성했는지 기록

소비자 공개

silver_runs / gold_runs
필요한 Glue 파티션을 등록한 뒤 공개 완료 실행을 목록에 기록

ETag ≠ Kafka 완전성. 처음과 끝에 같은 S3 객체를 확인해도 Kafka 메시지 100개 중 S3에 80개만 도착했을 가능성은 남아 있어. 현재 coverage_status=UNVERIFIED는 이 구분을 정직하게 표시하는 값이야.

Athena 공개 순서: 왜 manifest만으로 끝나지 않을까?

① Spark 계산결과별 Parquet 생성
② manifest 검증행 수·스키마·출력 위치 확인
③ Glue 등록run_id 파티션 연결
④ 완료 목록silver_runs / gold_runs에 공개
⑤ 소비자 조회완료된 run_id만 선택

`current.json`이 가리키는 최신 Spark 결과와 Athena에서 조회할 공개 완료 결과는 다른 기준이야. 코드상 공개 기능은 구현됐지만 실제 AWS Glue 등록과 Athena 조회 검증은 별도야.

집계 보류와 0건

데이터 오류로 계산 불가인 값은 매출 0원이 아니야. refresh_holds에 보류 근거를 남겨.
